# Архитектура iVideoCutter

## Назначение

Автоматическая подготовка вертикальных коротких роликов на ПК с Windows и публикация в YouTube/VK.

## Компоненты

| Узел | Ответственность |
|---|---|
| `ui/main_window.py` | Интерфейс и запуск фоновых Python-процессов |
| `core/video_splitter.py` | FFprobe/FFmpeg, кодирование, подпись, музыка, нумерация |
| `core/cutter_service.py` | Применение сохранённых настроек к очередному видео |
| `core/telegram_watcher.py` | Получение видео и caption из группы, аудиопроверка, запуск нарезки |
| `core/upload_queue.py` | Упорядоченные серии, случайные папки, приоритет Telegram |
| `core/youtube_uploader.py` | OAuth, YouTube Data API, отчёт о загрузке |
| `core/vk_uploader.py` | VK API video.save, передача файла, фиксация результата |

## Обработка

1. Локальное видео выбирается в GUI либо watcher скачивает Telegram-файл.
2. FFprobe получает параметры контейнера; при необходимости выполняется предварительная нормализация.
3. FFmpeg формирует выходные MP4 в нужном режиме и продолжительности.
4. У частей одной серии одинаковое количество цифр номера: минимум три, при 1000+ частях — четыре.
5. Telegram создаёт видео в приоритетном каталоге. Исходный слышимый звук сохраняется; на беззвучное видео можно наложить музыку.
6. На следующем запуске YouTube/VK загрузчик получает список файлов. Telegram имеет абсолютный приоритет над обычными сериями.
7. После подтверждённого успешного ответа платформы путь записывается в JSON состояния именно этой платформы.

## Правила очереди

- `output/output_1`, `output/output_2` и т.д. — независимые серии.
- Порядок файлов внутри серии фиксируется в JSON при сканировании.
- Между обычными сериями порядок выбора случайный.
- `output/telegram_priority` всегда проверяется до рандомной очереди.
- Если в Telegram-папке остался один ожидающий ролик, пачка состоит из одного ролика — старые серии **не добираются**.
- YouTube и VK имеют независимое состояние: успешная публикация на одной платформе не помечает файл опубликованным на другой.

## Инварианты и ограничения

**Не публиковать дважды**: метка успеха записывается только после успешного ответа API. Критический случай — ответ потерян после фактической загрузки, здесь нужна сверка по платформенному ID и ретраи.

**Один writer на state**: существующий JSON-state не транзакционная БД. Для параллельных процессов необходим lock/SQLite.

**Не читать незавершённые MP4**: сканирование папок на момент публикации может застать файл в процессе кодирования. Для надёжной промышленной версии следует писать во временную папку и атомарно перемещать готовые MP4 в очередь.

**Режим мгновенной загрузки**: не включён. Система публикует при следующем запуске YouTube/VK, а не немедленно после Telegram.

**Параллельность**: Telegram-временное изменение `config/settings.json` требует отсутствия конкурентного редактирования настроек GUI; предпочтительный следующий шаг — явная передача настроек в сервис, без записи общего конфигурационного файла.
